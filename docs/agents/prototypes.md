# Prototypes

A prototype is throwaway code that answers one question by giving the user something to use and react to. In this project that is a small egui app the agent launches and watches while the user drives it. The user never narrates what they did and never types a command.

## Branch and PR

- Each prototype gets its own branch, `prototype/<name>`, and a **draft** PR titled `PROTOTYPE: <what it prototypes>`. Its body opens with `Closes #<issue>`, so the PR shows in the issue's Development panel (`docs/agents/issue-tracker.md`, "Linking a pull request to its issue").
- Label the prototype's issue `prototype`. When a map charted it as `wayfinder:prototype`, swap that label for `prototype` as you take the ticket. Once the draft PR is open and the prototype awaits the user's session, add `ready-for-human`, so `gh issue list --label prototype --label ready-for-human` lists every prototype waiting on the user.
- The PR description states the question the prototype set out to answer, plus a running Q&A of what it showed. Update it as answers land.
- When the prototype session ends, post the resolution comment (below) on the prototype's issue and close the PR unmerged. Decisions go back into real code or docs through their own PRs.
- To carry a prototype onto a newer `main`, squash it onto `origin/main` rather than replaying its commits, and three-way merge each patched module copy: `git merge-file <copy> <src at the old merge-base> <src on origin/main>` keeps the `PROTOTYPE` patches on today's code. Then rerun the smoke pass. The rewritten branch needs a force push, which auto mode refuses whatever the user says in chat: give the user the command to run with `!`, and offer to put it on their clipboard with `wl-copy`.
- To rebuild a prototype from scratch on today's `main` (the Reconcile prototype, #374, moved from a stand-in Register to the real App), commit the rebuild on a branch from `origin/main`, then `git merge -s ours origin/prototype/<name>`. The push fast-forwards, so no force push is needed, and the PR's diff against `main` shows only the rebuild.
- Once the PR is closed, remove the prototype's local worktree and branch: `git worktree remove .claude/worktrees/<name>`, then `git branch -D prototype/<name>`. The remote branch stays as the PR's record.

## Shape

- Put it next to the code it serves, as an example directory named `<name>_prototype`: e.g. `crates/balanced_ui/examples/register_prototype/main.rs`. Run it with `cargo run -p balanced_ui --example register_prototype -- [--variant <key>] [--log <dir>/events.jsonl] [--control <dir>/control.txt]`.
- Add only dev-dependencies: `balanced_prototype_harness` (the observation harness, below), `eframe`, `egui_extras` and `serde_json`, each as `name.workspace = true` (add a missing one to `[workspace.dependencies]`, pinned with the other egui-family crates).
  - Put them in the crate's one `[dev-dependencies]` table. When a rebase brings in a table `main` added, git keeps both tables without a conflict and cargo then refuses the manifest, so merge them into one. A conflicted `Cargo.lock` resolves to `main`'s copy; the next build adds the prototype's packages back.
- Use crates as published. When a feature turns out to need a vendored, `[patch]`ed or forked upstream crate, stop and put that to the user as its own decision, with the no-fork alternatives beside it.
- `cargo xtask clippy` lints examples (`--all-targets`), so open `main.rs` with a crate-level `#![allow(...)]` for the pedantic and restriction lints a prototype trips.
- Feed it fixed-seed stub data at realistic volume (thousands of rows where the real thing will have them), generated by a small in-file LCG rather than a `rand` dependency. State lives in memory. A prototype on the real App writes its scenario into a scratch data file through `Ledger::apply`, then empties the undo history before the App opens it: drop the ledger, call `balanced_store::Store::open(path)?.clear_stack(Stack::Undo)`, and reopen it with `Ledger::open`. Otherwise Undo starts enabled and undoes the scenario (#374). Before the first launch, check that derived figures look plausible (balances, totals, signs): implausible numbers pull the user's attention off the question.
- Before writing UI code, read the Gotchas in `docs/practices/egui.md`: they list traps every prototype meets, such as glyphs the default fonts draw as empty boxes.
- Open the window maximized: `ViewportBuilder::with_maximized(true).with_inner_size([1600.0, 1000.0])` in the `NativeOptions`, plus `ctx.send_viewport_cmd(ViewportCommand::Maximized(true))` once on the first frame (a `maximize_sent: bool` on the app). XWayland ignores the builder flag, so without the first-frame command the row-edit prototype (#356) opened at eframe's default 800×600, 400×300 points at the user's 2× scale, with the dock filling the window. At the default size, the dock plus the Account bar also left the register cut off at its money columns, the very columns a step was about.
- Skip tests, error handling and polish. Spend the effort on variants, toggles and the observation harness.
- Before building, gather what earlier prototypes settled: read the resolution comments the map's Decisions-so-far links to, and use the code that landed from them (e.g. the theme module) rather than restyling from scratch. Each variant applies those decisions, so the user's reactions are about this prototype's question. Recheck when you rebase onto a newer `main`.
- An example sees only a crate's public API. `balanced_core` and `balanced_i18n` import directly; a private `balanced_ui` module compiles into the example with `#[allow(dead_code)] #[path = "../../src/<module>.rs"] mod <module>;`, which leaves `main` untouched, as long as it has no `use crate::` lines: each one needs its own module pulled in the same way. `theme` now uses `crate::preferences`, which uses `crate::register_columns`, so the file picker prototype (#547) copied the one constant it needed (`LIGHT_DIALOG_WIDTH`) and kept egui's default look, since the look wasn't its question.
- Before building, post the plan on the ticket: variants, toggles, stub data, open questions, and the earlier decisions it applies.

## Variants and toggles

- Build 2–5 **variants** that differ in structure or interaction model, not colour.
- Dock all prototype tooling (variant switcher, toggles) in one panel along the window's right edge, added before the variant's own panels so every variant lays out in the remaining space. Style it as tooling, and let F4 collapse it to a thin edge. Floating overlays cover the design under review. A separate OS window can't stay above the app on Wayland: winit ignores window levels and parent windows there.
- Keys in the app window, while no text field has focus:
  - a letter per variant (`A`, `B`, `C`) and ←/→ to step through them;
  - a number key per toggle (`1`–`9`, then `0`), so the user can flip one back and forth to see where it changes the screen;
  - F2 opens a note, F3 drops a marker, F4 collapses the dock, F5 turns the spotlight on or off.

  Label every variant and toggle in the dock with its key. A `--variant <key>` flag picks the starting variant.
- Every menu item and button that would act in the real app logs a `command` event naming the Command it would emit (`would_emit`), so the session records what the real app would do.
- Tag each toggle as applying to one variant or to all. Toggle state and shared data (selection, sort) survive a variant switch, so the user compares like with like.
- Users pick per step, so their answers mix variants (A's chrome with B's balances). Give each part the agenda asks about separately its own placement setting, read by every variant, so the whole-picture step shows the user's own mix. When a part was fixed to one variant instead, the register prototype needed a patch and a second launch before the user could judge the whole.

## Observation harness

The agent follows the user through the app's own output. Build these in:

- **Event log**: JSONL at the path given by `--log <path>` (a fresh directory in your scratchpad for every launch: screenshot numbers restart at `001` each launch and overwrite the last run's). One line per event, with a timestamp:
  - clicks, named by widget (`payee cell, row 1204`), not coordinates;
  - focus gained and lost, with the cause (click, Tab, app moved it);
  - typing: each keystroke tied to its field, and Tab, Enter, Esc and arrows as their own events;
  - app events: variant switches, toggle flips, saves and cancels with the Commands they would emit, suggestions offered and picked, sort changes;
  - one event per finished scroll gesture (rows moved, duration, worst frame), and a perf sample about once a second.

  Log intent, never a raw mouse-position stream.
- **Screenshots**: the app captures its own window (`ViewportCommand::Screenshot`) as PNGs beside the log on every variant switch and toggle flip.
- **F2** opens a one-line note box written into the log; **F3** drops a marker plus a screenshot.
- **Spotlight** dims the window except outlined cut-outs around the named controls, so the user's eye lands where the step points. Its targets match, case-insensitively as substrings, the names given through `track` and `region`; only the outermost matches are cut out and outlined, so a region hides the rows inside it that also match. **F5** or the dock's "Spotlight (F5)" row (`dock_spotlight`) turns it on or off; each change logs a `spotlight` event (`on`, `targets`, `matched`: the outermost matches drawn, `cause`) and a screenshot, and a `spotlight_unmatched` event means nothing on screen matched.
- **Prompt panel** runs along the bottom of the window and shows the agent's next instruction, so the user follows the walk-through without switching to the terminal and answers with F2. `prompt <text>` sets it and flashes the panel (each literal `\n` is a line break; the panel draws in the app's fonts, so write "then" where you'd type →, which shows as an empty box) and `prompt off` clears it; **F6** or the dock's "Prompt (F6)" row (`dock_prompt`) puts it away, and the next `prompt` brings it back. Changes log `prompt` and `prompt_shown` events. Its last line always shows the window's fps, frame count, position, size and focus, so keep per-window diagnostics out of the app's content area.
- **Control file**: you append commands to the file at `--control <path>`, one per line; each is logged as a `control` event followed by its effect. Commands already in the file at launch run first, which sets up an opening scenario. A verb that redraws the screen (`reload`, `account`) leaves nothing tracked until the next frame, so a `click` straight after it logs `control_unknown`: put `wait 500` between them. A `click` verb that injects pointer events sends the move, the press and the release in one frame's batch. A covered XWayland window draws about once a second, so a press and a release a frame apart land a second apart, and egui counts no click: none of #374's first scripted clicks registered. Make a data-reset verb reopen the account it showed, or every scenario after it clicks into an empty tab, as the first smoke pass of #483 did. Every prototype supports `variant <key>`, `toggle <key> [on|off]`, `screenshot [label]`, `dock on|off`, `reload` and `quit`, and the harness itself handles `spotlight <target>[; <target>…]` (sets the targets, `;`-separated because names hold spaces and commas, and turns it on) and `spotlight off|on` (keeps the targets), plus navigation verbs for its own domain (the shell layout has `account <index|name>`, `tab <index|name>` and `row <n>`).
- **Wayland throttling**: a covered native-Wayland window gets no frames, for 15 minutes and more, so control commands queue until the user brings it forward; twice a window left covered for most of an hour never drew again, even when shown, and ignored its own close button. Under XWayland the same window applied every command within about a second while covered, but a minimised window drew nothing under XWayland too, so commands queued until the user restored it (`perf` events stop; tell the user to bring the window back); step 4 of Running a session says when to use which. A background thread reads the control file whatever the backend, and `quit` always lands: the thread exits the process once no frame has run for 2 s, so it is how you close a window the user reports as frozen.
- **Stuck keyboard on native Wayland**: typing into a native-Wayland prototype (the F2 note box) once wedged GNOME's input method, IBus, so every key in every app timed out, and closing the prototype did not clear it. `journalctl --user --since "15 min ago" | grep 'Error processing key on IM'` confirms it; `ibus restart` fixes it, no reboot needed. When the user reports typing hanging, check for that line and run `ibus restart`.
- Screenshots wait 350 ms so scroll animations and egui's multi-pass layout settle, and land as `<seq>-<label>.png`. Each one is then encoded as a full-resolution PNG inside a frame, so a script holds its next command about 2.5 s after a screenshot, or a later verb (`reload`) runs before the capture: #374's "finished" screenshot showed the reloaded data. The log also records `window_focus` changes and `session_end`.

The harness is the `balanced_prototype_harness` crate on `main`. Use it as a dev-dependency, not a copy, and follow the contract in its crate docs (`cargo doc -p balanced_prototype_harness --open`, or `src/lib.rs`): build a `Harness` from `Args::from_env()`, call `begin_frame` first and `end_frame` last in `ui()`, `track` named widgets, name larger areas with `region` each frame, draw `dock_spotlight` and `dock_prompt` in the dock, call `prompt_panel` before the `CentralPanel`, and log `session_end` from `App::on_exit`. When a prototype needs a harness feature that's missing, add it to the crate in its own PR from `main`, with tests, rather than patching it inside the prototype. Rebase the prototype branch onto that PR's branch so the session uses it now, and set the prototype PR's base to that branch (`gh pr edit <n> --base <branch>`), so its diff shows only the prototype. Leave `gh stack` out: a stack is for merging, and the prototype PR is never merged. The shell layout prototype (`prototype/shell-layout`) is a full example of an app wired to it.

## Running a session

The user learns what to look at from you. Drive the session through an **agenda**: the questions the prototype must answer, in the order the user should meet them.

You drive the prototype as well as the conversation. Through the control file you switch variants, flip toggles, and open the account, tab or row each step needs, so the user's hands stay on looking, trying and reacting. Each step takes the user through every variant and toggle that bears on its question, side by side, and you make each switch yourself as the step reaches it.

1. Before launch, write the agenda into the PR's Q&A, one entry per question.
2. Before the first live session, run a **smoke pass**: a scripted launch that finds the bugs the user would otherwise hit in their first minutes. The calculator-popup prototype (#214) skipped it, and its first session hit five such bugs in ten minutes.
   - Pre-seed the control file with each agenda step's scenario: its variant switches and toggle flips, a `screenshot` after each, and every control-file verb the prototype offers. Ask for clearance as a smoke run (step 3), launch, then read every screenshot and the whole log.
   - Keep the script in its own file in your scratchpad and copy it to a fresh run directory's `control.txt` for each launch. The harness empties the control file as it reads it, so a copy of the last run's `control.txt` is empty: in #483 a rerun launched on one and sat idle until the user closed it.
   - Check:
     - the window opened maximized, read off the prompt panel's last line in the first screenshot; if it didn't, stop the run and add the first-frame maximize from Shape before reading further;
     - no glyph draws as an empty box (the Gotchas in `docs/practices/egui.md`);
     - every control fits at the user's screen width, read off the prompt panel's last line rather than assumed: at 1228 points the calculator's entry row cut off its Enter button;
     - each earlier decision the plan says it applies behaves as the built code does. Read that code for what it does at the edges, e.g. when a field loses focus: the register replaces typed arithmetic with its result (#90), and the prototype never did;
     - each stand-in for a built control looks the way the built control looks. Copy the built control's drawing code (sizes, frames, fills) rather than redrawing it with default egui widgets: the calculator prototype's calendar used framed buttons in uneven columns, and the user judged its new Today button on "the formatting of the entire control" until it was redrawn as `date_field.rs` draws it;
     - each field takes empty and edge inputs: an operator typed on an empty field seeded a bare `+` the reader refused, so Enter did nothing;
     - the harness still works with each popup open: the calculator popup filtered every text event in the window, so the F2 note box took no letters;
     - each control verb leaves the screen the next verb assumes. Follow every action verb with `cancel` and a `screenshot`, and switch variants with each variant's surface open: in the Category List prototype (#361), `cancel` on a confirm closed the whole list, so every later scenario ran with nothing open, and switching from B's tab to C left the tab drawn behind C's Dialog.
   - Fix what it finds before the user drives it. Judgement calls, such as a refusal shown only as "…", are the session's to surface.
   - A bug that looks like the shipping app's goes on the tracker only once a harness test on `main` reproduces it; name that test in the ticket. A `#[path]` module may be a patched copy, so before calling the code real, diff it against `src/` (`diff crates/balanced_ui/{src,examples/<name>_prototype}/<module>.rs`). #498 was filed from #483's smoke pass as real Register code, but it came from the prototype's patched `register.rs` and never reproduced on `main`.
3. Ask the user for clearance to launch, for the smoke pass and again for the session. Every launch needs it, including your own scripted control-file runs: the window opens on the user's desktop and takes keyboard focus, so it logs whatever they were typing elsewhere. An unfocused window is also throttled on Wayland, so a scripted run stalls while the user works in another app.
4. On a yes, start it yourself as a background process. Pick the backend by the question. The app ships as a native Wayland window, and XWayland changes how it feels: frames pass through an extra X server (different pacing and latency), fractional scaling draws at one scale and stretches the result (softer text and lines), touchpad and high-resolution scroll events arrive translated, and the harness's frame and scroll timings describe XWayland's pipeline. So:
   - **look or feel** (animation, scrolling, rendering, theme, performance): launch natively. A covered window queues your commands until the user looks back, which is harmless, but one left covered for most of an hour can freeze for good. So watch for frames stopping (`perf` events cease): once a native window has drawn nothing for 20 minutes, send `quit`, and when the user next writes, tell them it was closed while they were away and relaunch on their word;
   - **behaviour** (keys, focus, parsing, messages, flows): launch under XWayland, `WAYLAND_DISPLAY= cargo run -p <crate> --example <name>_prototype -- …`, which keeps applying commands while covered. Tell the user it's up, along with the keys that drive it themselves (variant letters, toggle numbers, F2–F6). Watch the log with the Monitor tool, filtered to `note`, `marker` and `session_end`; read the rest of the log when a step needs it.
5. Guide one agenda question at a time, numbered `Step <n>/<total>`. For each step, give the user:
   - **context**: what the variants or toggles in play change, and why it matters for the question. Show each option with figures from the screen in front of the user ("this row's Balance reads 5,027.64 now; with toggle 9 on it reads −924,381.85"), read off a screenshot or the log; a choice the user can't see is a choice they can't make. When Quicken has an answer, say what it does beside your recommendation;
   - **look at**: where on screen the variant in front of the user differs, region by region. Spotlight stays off by default: turn it on only when the step points at something easy to miss, target the specific widget rather than its whole region, and send `spotlight off` before the user explores freely. Name every toggle that applies to it, with its key, in this step's first message, not after the user asks. Save comparisons with a variant the user hasn't reached yet for when you switch to it;
   - **try**: one action per message, in a scenario you have already set up through the control file, down to the open dialog when the try is reading one (the Category List's `delete` verb opens its confirm). The user acts on that one action, then answers; you make the next switch and give the next action. A two-part try ("click Delete, Cancel, press 2, then Delete again") lost the user in the Category List session (#361) until the agent reset the screen to the dialog. When the step compares variants or toggles, switch them yourself one at a time and say what changed after each switch. When the user flips a toggle and judges it, check the log for the state they were looking at and name it in your reply ("that was with it off").
     A data reset empties the undo history, so a step about Undo first makes a saved change to undo (flag a row), or Edit → Undo is greyed and reads as a bug.
     While a text field has focus (an error keeps it in the cell), variant letters and toggle numbers type into the field, so when a try ends in a field and the next action is a variant or toggle, tell the user to click it in the dock or press Esc first;
   - **notice**: what to pay attention to while trying it.

   Put the step's next move in the prompt panel as it comes up: `prompt Step <n>/<total> · <the next action, question or thing to notice>`, a line or two, replaced as the step advances. The terminal message carries the full context; the panel carries only what to do or answer now.

   End the step by asking for their reaction.
6. Watch the event log as it grows (the Monitor tool), and read screenshots when a variant or toggle changes or the user drops a marker. Log events are evidence to use when the user next writes. Answer only the user's messages, and use the log in that answer.
   - Leave the dock as the user set it. When they collapse it, switch and flip for them through the control file without reopening it.
   - A Monitor expires after 30 minutes. When one expires with no events, read the log's last `perf` event before re-arming: a gap means the window has stopped drawing and your queued commands haven't run, so tell the user to bring it back (step 4). In #361 the window sat minimised for 50 minutes behind two silent re-arms.
   - When the user leaves mid-session, send `quit` and add a "Resume at" line to the PR: the next step, and the control commands that set it up. The next session relaunches straight onto that step.
7. Turn what the log shows and the user doesn't say into follow-up questions: hesitations, Esc right after starting an edit, Tab landing somewhere the user leaves at once, a control never touched, slow frames.
8. When the user's message refers to "this" or "here", line it up with the log by timestamp.
9. A step closes on the user's answer. The log is supporting evidence of what they saw and tried, not a gate: some questions are easy to picture, and the user may answer from a glance or before trying anything. Raise a mismatch only when the log shows something that changes the answer, e.g. the user picked a variant they never opened. Record the step as a Q&A entry on the PR, citing log events where they exist. Then set every variant and toggle the step compared to the user's pick through the control file, and move to the next step: the next step's questions assume the screen shows what the user chose.
10. The session ends when every agenda question has an answer. Post the resolution comment, close the PR unmerged, then remove the local worktree and branch.

To stop the prototype, send `quit` through the control file, or stop the background task. The example binary can outlive its `cargo run` wrapper, so confirm with `pgrep -f '^target/debug/examples/<name>_prototype'`: the `^` keeps `pgrep` from matching your own shell command, which contains the same path.

For screenshots in the PR description, run a scripted session (it needs clearance like any launch) with the commands pre-seeded in the control file, commit the PNGs under `docs/prototypes/<name>/` on the prototype branch, and embed them with `raw.githubusercontent.com` URLs.

## Resolution comment

When the session ends, post one comment on the prototype's issue with this shape, then close the issue and append the context pointer to the map's Decisions-so-far. The pointer links to this comment, so the first line answers the ticket without scrolling.

```
**Resolution:** <one or two sentences: the answer the prototype gave to the ticket's question>

| # | Question | Answer | Tag | Reversibility | Evidence |
|---|----------|--------|-----|---------------|----------|
| S1 | <agenda question> | <what was chosen> | firm / leaning / coin-flip | cheap / expensive | <user quote, log events, screenshot> |

**Variants:** <each variant: chosen, merged into the winner (name the parts), or dropped, with the reason>

**Observed in the log:** <what the log showed beyond what the user said: hesitations, ignored controls, slow frames, or "none">

**User-decided:** <the `coin-flip` and `expensive` calls the user answered, with their reasoning if given>

**Assumed, shout if wrong:** <answers taken from the log or defaults without asking>

**Revises:** <earlier decisions or map entries this contradicts, or "none">

**Follow-ups:** <new tickets, ADRs, or `GLOSSARY.md` terms it produced, linked, or "none">

**Prototype:** <the closed draft PR and its branch>
```

- List every agenda question as a table row, numbered by its step.
- Use the tags defined in the Grilling section of `CLAUDE.md`. Here `firm` means the user chose it explicitly. In Evidence, cite log events and screenshots where they exist, and write "user's answer" where the user answered without them.
- Write `none` in an empty section.
