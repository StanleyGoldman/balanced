# Testing

## Pick the lowest layer that can catch the bug

1. **Unit tests in `balanced_core` and `balanced_i18n`**: plain `#[test]`, plus `insta` text snapshots for structured output (formatted amounts, exports, reports). These need no GPU and no egui, and they are what mutation testing checks.
2. **UI interaction tests in `balanced_ui`**: `egui_kittest`'s `Harness`, finding widgets by AccessKit role and label, clicking and typing, then asserting on state or node properties. These need no GPU and run on every OS.
3. **Image snapshot tests**: a few, only for layout-critical views (the Register, the Account bar). See [Image snapshots](#image-snapshots).

Prefer a core unit test to a UI test, and a UI interaction test to an image snapshot.

## Writing tests

- Each test checks one behaviour, with setup, action and checks visibly separated.
- Prefer exact comparisons (`assert_eq!`) to partial ones (`contains`).
- Keep fixtures small and tests fast. Mutation testing runs the suite once for every mutant.
- Spell a partly typed name in a test as a fragment `typos` reads as a word or leaves alone, such as "Tratt" for Trattoria Roma or "Fres" for Fresh Market. `cargo xtask ci` runs `typos` over test code and test names, and it rejects a fragment or a name it reads as a misspelled word. The same goes for any doc that quotes such a fragment.
- Test behaviour that could plausibly break, and skip trivial wiring.
- Tests run against a real in-memory `Ledger`, not mocks.
- A test that needs a write to fail breaks the path, not the permissions. CI runs as root, which writes through a read-only directory or file, so a `chmod` test passes locally and fails in CI. Make the name longer than the 255-byte limit, or put a directory where the file would go.
- A test that a sum overflows `Money` reaches it through an `Amount` edit (`Decimal::MAX.trunc() / dec!(100)`), not through `Ledger::with_accounts`. The data file holds each amount as an `i64` of minor units, so a ledger built with an amount that large panics in setup with `AmountOutOfRange`, while an edit is checked against `Money` before it is written. `an_edit_that_takes_the_cleared_balance_out_of_range_is_rejected` in `crates/balanced_core/src/ledger.rs` shows the shape.
- `unwrap()` belongs in a `#[test]` function. A helper function in test code writes `expect("why this can't fail")`. Under `#[cfg(test)]` review enforces this, not clippy: `allow-unwrap-in-tests` (`clippy.toml`) lets `unwrap()` through anywhere there, helpers included. In an integration test file under `tests/`, clippy rejects `unwrap()` and `unwrap_err()` in a helper, since only the `#[test]` functions count as tests there.
- A changed `insta` text snapshot fails its test and leaves a `.snap.new` beside the `.snap`. Read the diff (`cargo insta pending-snapshots`, or the test's output), then accept it with `cargo insta accept`. Moving `.snap.new` over by hand keeps an `assertion_line:` header that the committed snapshots don't carry.

## UI tests

- Drive the UI the way a user does: `node.click()`, or `focus()` then `type_text()`. Don't write into internal state to set up a UI test. `TextEdit` ignores AccessKit value-setting in egui 0.36.
- `node.click()` clicks the centre of the node's rect, even when the widget is scrolled out of view. In a heavy Dialog's scrolling body, or in a `ComboBox` list long enough to scroll (a Parent picker of every category), that click lands on the dimming backdrop and cancels the Dialog, and the test fails later with "No nodes found". Scroll the widget into view first: `node.scroll_to_me()`, `harness.run()`, then `click()`.
- The editing row's buttons (Save, Cancel, Split, More actions) draw over its cells to the left of Actions, at default widths Balance, Clr and Flag. Every cell they cover whole leaves the AccessKit tree while the row is editing, so a query for the editing row's own Clr or Flag cell finds nothing. Flag the editing row through More actions, and read its Flag or Clr cell once the row is saved or its changes discarded. Other rows' cells stay in the tree and take `click()`.
- A light Dialog closes as Cancel on any click on its dimmed backdrop, which covers everything else on screen. A click on an Account bar button or a cell while one is open dismisses it, so a later "no prompt shown" check passes for the wrong reason. Assert the Dialog's state right after the action that should open it (or not), before the next click.
- Find nodes by role and label (`get_by_role_and_label`), never by screen position. This holds for absence too: assert that no node has the role *and* label (no cell editor labelled Payee), since a bare role (no `Role::TextInput` at all) breaks when any field joins the window, as the filter bar's Search box did. To split nodes by height, measure from another node's rect (below the Register's Date heading), never a fixed y that a new row above shifts.
- The Register lays out only the rows in view, so AccessKit holds no node for a row scrolled out of it. An assertion that something is absent proves it only in view: open an account short enough to fit, such as Joint Checking, not Household Checking's 20,000 rows, and red-check that the assertion fails once the thing is drawn.
- A Register combobox list lays out only the rows in view too, about eleven, so `query_all_by_role(Role::ListBoxOption)` misses the rest, and the Create row at the end can be among them. To assert entries far down the list, type text that narrows it to them, as `[` does for the `[Account]` entries.
- `get_by_role_and_label` panics when two nodes match, and some labels name two buttons: the top-level tabs Investing and Property & Debt share their names with Account bar headings. Pick a label only one node has (the Banking heading), or query inside the node that holds the one you want, since a kittest node is `Queryable` too: `harness.get_by_role(Role::TabList).get_by_role_and_label(..)`.
- A menu item with a Shortcut has its Shortcut text in its AccessKit label, after a space: find Undo as `"Undo Ctrl+Z"`, not `"Undo"`.
- A Register cell's AccessKit label is its text, so an empty cell's label is empty and every empty cell reads the same. To assert that the cell cursor landed on an empty cell (Deposit after a payment), find the column heading whose x-range holds the cursor cell's centre, as `cursor_column` in `crates/balanced_ui/tests/keypad.rs` does.
- A `Label`'s text is its AccessKit value, and its label is empty, so `get_by_label` misses a message shown in a `Label` (a bubble, the Status bar). Find it by role and value: `query_all_by_role(Role::Label)` and `accesskit_node().value()`.
- A kittest node's `rect()` panics with "Every egui node should have a rect" on a container with no bounds of its own, such as the Status bar (`Role::Status`). Measure a widget inside it instead: `harness.get_by_role(Role::Status).get_by_role_and_label(Role::Label, ..).rect()`. On a widget that isn't focusable, the panic means the app gave its node no bounds (see [egui](egui.md#accessibility)).
- A query that panics with `Focused ID #… is not in the node list` means egui's focus is on a widget no longer drawn, such as a cell editor that closed while a Dialog was open, so the Dialog's `FocusReturn` gave focus back to nothing. A screen reader loses its place the same way: fix where focus goes in the app.
- `accesskit_node()` returns an `accesskit_consumer` node, whose `supports_action` takes a filter as well. To ask whether a widget accepts a click, read the raw node: `node.accesskit_node().data().supports_action(Action::Click)`.
- Typing in a Payee or Category cell completes the text with the first entry that starts with it (Inline completion) and highlights that entry, or else the list's top match, and Tab or Enter takes the highlighted entry: "fresh" commits as "Fresh Market". To commit the text as typed, press ↑ first, which clears the highlight, or Backspace after typing, which drops the completion and the highlight. Delete also removes the completed text.
- Text in a Payee or Category cell that matches an entry opens its completion list, and the next click elsewhere only closes the list: the cell cursor stays put. When the click itself is under test, type in a field with no list (Payment, Memo).
- A click on a Register cell only moves the cell cursor. Enter then opens the cell's editor holding its saved text; typing opens it holding just the typed text.
- egui handles a click in drawing order. With a cell editor open, a click on a row drawn below it reaches that row after the editor has lost focus and committed, so the clicked cell sees no edit open. To test how a click on another row treats an open edit, click a row drawn above the open cell (an earlier date in a stub account: in Everyday Checking, Fresh Market 9/5/2026 sits above Shell 9/15/2026), and red-check it, since a click below passes without reaching the code under test.
- A refused save (Enter, Ctrl+Enter, leaving the row) opens the "Can't save this transaction" Dialog, whose reason is the same text as the amount bubble, the date bubble or the Status bar message. Assert the Dialog's heading as well as the reason, or the reason matches the bubble's `Label` and the test passes with no Dialog. To test a bubble, refuse with Tab, which moves within the row and keeps the bubble.
- A Dialog's title is its window node's label, not a `Label`'s value, so a search of `Label` values never finds it, open or closed. Assert a Dialog is open, or has closed, through a node inside it: one of its fields, such as the Split dialog's `Line 1 category`.
- A Register row keeps its changes until it is saved, and shows them meanwhile, so a cell showing the new text proves nothing was saved. Assert a save through what only the ledger changes: Undo enabled in the Edit menu, or the row after Esc, which throws away whatever wasn't saved.
- Enter saves the row and, with "Enter moves to the next row" on (the default), opens the next row's cell in the same column, so a key pressed after it goes to that cell: Ctrl+Z undoes typing there, not the save. Press Esc first to close it.
- A UI test that saves Preferences checks `version` and the keys it changes, with `balanced_ui::testing::check_saved_preferences`, so a new Preference leaves it alone. The full `preferences.toml` text lives in one test, `the_file_holds_its_version_and_every_preference` in `crates/balanced_ui/src/preferences.rs`.
- Labels in tests use the pinned test locale, `en-US`. A test of another locale uses that locale's labels (see [i18n](i18n.md#tests)).
- Double-clicks need `with_step_dt(0.01)`. With the default 0.25 s step, the second click arrives too late.
- AccessKit carries no text colour. To check a colour (a negative amount), read the last frame's text shapes: `harness.output().shapes`, each `Shape::Text`'s galley sections and `override_text_color`. The theme's negative colour is `visuals.error_fg_color`. `amount_colours` in `crates/balanced_ui/tests/main_window.rs` does this.
- Hover tooltips need the default step. After `node.hover()` and `run()` at 0.25 s, the tooltip shows as a `Label` and in a render. Under `with_step_dt(0.01)` it never rendered, even after `run_steps(100)`.
- `egui_kittest` never calls `eframe::App::raw_input_hook`, so a key the hook takes (Tab in the Register) reaches egui's focus navigation in a test as it never does in the app. Send such keys through the hook: take the input with `std::mem::take(harness.input_mut())`, push the event, call `harness.state_mut().raw_input_hook(&ctx, &mut input)`, put the input back, then `step()`. The `send` helper in `crates/balanced_ui/tests/register.rs` does this.
- `Harness::output()` holds only the last frame's output, and `run()` keeps stepping until repaints stop. Output that lasts one frame, such as a `ViewportCommand` sent from `App::logic`, is gone by the time `run()` returns. Step to that frame instead: after a `click()`, one `step()` plays the click, and the next runs the `logic()` that applies the Command it sent.
- `step()` plays each queued event in a frame of its own. `key_press_modifiers` queues four (modifiers down, key down, key up, modifiers up), so one `step()` runs four frames and passes the one-frame output by. To step to a chord's output, queue a single `Event::Key` that carries its modifiers with `harness.event(..)`.
- `Harness::run()` panics if the UI keeps asking for repaints. A UI that animates needs mocked time in its tests.
- Each Command sent from `App::logic` is applied in the next frame, so a chain of them (a Dialog's answer, then a save, then the ledger's answer, then Quit) can outrun `run()`, which panics with "exceeded max_steps (4)". Step such a chain with `harness.run_steps(n)`.
- `egui_kittest` keeps a viewport's `events` in the harness input from frame to frame, where eframe clears them. To request the window's close, push `ViewportEvent::Close` into `harness.input_mut().viewports.entry(ViewportId::ROOT).or_default().events`, `step()` once, then clear those events before `run()`. Left in, `close_requested()` stays true every frame and `run()` exceeds its step limit.
- To act while a leave-row prompt's save is on its way (applied by the ledger, but its answer not yet taken by the Register), request the window's close. A click can't land there: its Command queues behind the save, and `App::logic` applies queued Commands in order. `logic` applies them, then checks `close_requested()`, so the close lands after the stub ledger (`Ledger::stub()`) applies the save and before the Register takes its answer in that frame's `ui`. The window lasts one frame. After `click()` on the prompt's Save, one `step()` plays the click and applies the answer (`LeaveStep::Answered`), and the next sends the save (`LeaveStep::Saving`); push `ViewportEvent::Close` then, and `step()`. A close in the frame after a click that sends a Command, such as an account in the Account bar, lands after that Command: `open_then_close_before_applied` shows the shape. Find that frame with a temporary `eprintln!` trace in `logic`: a guessed frame misses the window, and the test passes on the unfixed code. `save_then_close_while_on_its_way` in `crates/balanced_ui/tests/leave_row.rs` shows the shape. To act a frame earlier, while the answer waits at `LeaveStep::Answered`, push the close after the first `step()`, as `answer_then_close_before_carried_out` does. A close at either step looks the same in the test, so make the leave that asked something else, such as opening another account, or the test passes on the unfixed code.
- To have the ledger apply two Commands in one frame, such as a save of the editing row and another change, play the key that sends the first with one `step()`, then queue the second with `balanced_ui::testing::send_domain` and `run()`. `App::logic` applies both in the next frame. No user action can land a second Command there. `press_enter_with` in `crates/balanced_ui/tests/cant_save.rs` shows the shape.
- `MainWindow::open_dialog` refuses a Dialog while another is open; only the leave-row prompt and "Can't save this transaction" open over one. So a second confirm never takes the open one's place. To force a Dialog open while the Register's save waits on a confirm of its own, queue the forced `AppCommand::OpenDialog` through a `balanced_ui::testing` helper, then press the key that saves. `App::logic` opens the queued Dialog before the frame draws, the key's own confirm request arrives behind it, and `open_dialog` refuses that request. Have the helper drop egui's focus (`memory.surrender_focus`) before it queues the Dialog. Otherwise the Dialog remembers the cell editor as the widget to give focus back to, the key closes that editor, and closing the Dialog panics with `Focused ID … is not in the node list` (above).
- A test that needs the ledger to refuse a Command it sends itself proves the refusal first: assert that Command alone is refused, or reuse one an existing test already sees refused. A Command the ledger quietly takes reads as applied, and the test can still go red on its own assertion for that wrong reason. The closed transfer of `with_closed_transfer` in `crates/balanced_ui/tests/cant_save.rs` refuses a change to its amount, but takes a change to its payee.
- Today's date comes from `balanced_ui::Clock`, which the App owns. Build every test App with `Clock::fixed(date)` (feature `test-support`) so it runs the same on any day, and give each test file `required-features = ["test-support"]` in the crate's `Cargo.toml`. So run one file as `cargo nextest run -p balanced_ui --features test-support --test <file>`; without the feature cargo refuses the target. `balanced_ui`'s own unit tests (`--lib`) need the flag too: without it they fail to compile, with no `App::on_ledger`. `balanced_core`'s `upgrade` test needs the same flag: `cargo nextest run -p balanced_core --features test-support --test upgrade`. `clippy.toml` bans `SystemTime::now`, `Instant::now` and jiff's `now` everywhere else; the prototype harness, which times sessions, is the one exception.

## Image snapshots

The tests live in `crates/balanced_ui/tests/snapshots.rs`, and the images in `crates/balanced_ui/tests/snapshots/`.

- **Source of truth:** Linux with lavapipe, Mesa's Vulkan software rasterizer (`mesa-vulkan-drivers` on Debian and Ubuntu). `balanced_ui::testing::app` accepts no other adapter, so every Linux machine draws the same pixels. On other OSes `cargo xtask snapshots` skips them.
- **Writing one:** build the App with `balanced_ui::testing::app(scheme)` and check it with `check_snapshot`, which holds the project thresholds. Mark the test `#[ignore]`, with a reason naming `cargo xtask snapshots`, so `cargo xtask test` skips it. After clicking, send `Event::PointerGone` and `run()`: kittest draws the pointer and its hover into the image.
- **Running:** `cargo xtask snapshots`.
- **A crash is not a diff:** a snapshot test can die with `SIGSEGV` (signal 11) inside lavapipe, with no image compared. nextest runs each test in its own process, so the crash fails only that test, reported as `SIGSEGV` rather than `FAIL`, and the rest still pass or fail on their images. Rerun `cargo xtask snapshots`. A test that crashes again is a bug to investigate.
- **Reviewing a failure:** kittest writes `<name>.new.png` and `<name>.diff.png` beside the snapshot (both gitignored). In CI they are in the `snapshot-diffs` artifact, linked from the `test` job's summary. Look at both images and name every changed region. A change the code was meant to make gets updated; anything else is a bug to fix.
- **Updating:** `UPDATE_SNAPSHOTS=1 cargo xtask snapshots` rewrites the failing snapshots. Commit each new PNG with the code that changed it, staged with `git add -u crates/balanced_ui/tests/snapshots/`. The ignored `.new.png`, `.diff.png` and `.old.png` sit beside them, and `git add` refuses a whole call that names one, as a `*.png` glob does. Say in the PR which views changed and why. A snapshot that fails on noise is fixed in the test setup; the thresholds stay put.
- **A merge conflict:** git can't merge a PNG, so a snapshot that both sides redrew stops a merge whenever `main` moves. Check out either side (`git checkout --theirs <png>`), regenerate it with `UPDATE_SNAPSHOTS=1 cargo xtask snapshots`, and open the new image to confirm it shows both sides' changes before you `git add` it. A PR whose snapshots overlap a busy area of `main`, such as the Register, can conflict again after each merge, so check `gh pr view <n> --json mergeable` after pushing.

## Coverage

CI measures line coverage and reports it; coverage gates nothing. The workflow's `test` job runs `cargo xtask coverage` where `cargo xtask ci` runs `test`: the same suite and doctests under `cargo-llvm-cov`, so the run that gates the merge is the one that measures. Locally `cargo xtask test` stays uninstrumented, and coverage isn't part of `cargo xtask ci`.

- **Where it shows:** the run's job summary; the `coverage` artifact (`html/index.html`, `lcov.info`, `summary.md`), on pull request and `main` runs alike; and, on a pull request from this repository, one comment. Each push deletes the earlier coverage comments and posts the new report (`.github/post-coverage-comment.sh`). A fork's pull request gets no comment, because its token is read-only.
- **What it counts:** lines and functions of the workspace, minus `xtask` and the `tests/` directories. Image snapshots run uninstrumented, in their own step, and doctests run but aren't counted. Tests inside `#[cfg(test)]` modules count their own lines, which lifts the figures a little.
- **Changed lines:** on a pull request, the share of the lines it adds that hold code and that the tests ran. A line with no code (a comment, a signature) isn't counted. Read it as a pointer to untested code; mutation testing (below) is what judges the tests.
- **Gating:** not done. UI painting code is hard to cover by line and easy to cover by accident, and a threshold invites tests written for the number. To gate anyway, add `--fail-under-diff <percent>` to the pull request step of the `test` job.
- By hand: `cargo xtask coverage [--base origin/main]` writes `target/coverage/`; it needs `cargo install --locked cargo-llvm-cov` and `rustup component add llvm-tools`. Failed tests' junit file is under `target/llvm-cov-target/nextest/`.

## Mutation testing

`cargo-mutants` mutates only `balanced_core` and `balanced_i18n` (`.cargo/mutants.toml`). Each mutant runs only its own crate's tests, so core logic has to be caught by core's tests.

- CI runs mutation testing after the merge, never on a pull request (ADR 0002). After each merge the `mutants` workflow tests the mutants in the diff that pull request brought into `main` (`cargo xtask mutants-landed`). Each night it tests one of seven round-robin shards of every mutant on `main` (`cargo xtask mutants-shard`), so all of it is tested once a week. Your pre-push gate is `cargo xtask ci` alone.
- Each surviving mutant gets one GitHub issue, labelled `mutant` and `ready-for-agent` (plus `mutant-timeout` for a timeout). The body holds the mutation, a permalink, a link to the pipeline that found it, and the command that runs that one mutant. Later runs comment "found again" with a link to their own pipeline and the line where the mutant now sits, close it when a test catches the mutant, or close it when the mutant is no longer generated. The issue is keyed by file, function and mutation, never by line, so edits elsewhere leave it in place.
- `cargo xtask mutants` is the by-hand tool for proving a mutant's fix: run the issue's reproduce command before and after your test, and the mutant goes from missed to caught. `--re <pattern>` tests every mutant whose name matches, wherever it is; `<base>` limits it to code committed since `<base>` (default `origin/main`). It needs `cargo install --locked cargo-mutants cargo-nextest`, and it reports missed mutants without failing. cargo-mutants 27.1.0 also tests every struct-field deletion mutant (`delete field … from struct …`) on any `--re` run without a diff, because those ignore name filters (cargo-mutants #632, fixed after 27.1.0). Ignore those extra results.
- Run it through `cargo xtask mutants`, never `cargo mutants` directly. On Linux the xtask runs it in a systemd scope capped at 8 GB with no swap. A mutant that makes a loop allocate forever fills RAM in seconds, before the per-mutant timeout fires, and an uncapped OOM kill takes the whole terminal session with it. On other OSes there is no cap.
- Write every loop over input so each pass provably consumes something, checked in the loop itself (see `split_number` in `balanced_i18n`'s `money.rs`). A mutant then fails the tests instead of spinning. Hold that check in a type, as `NonZeroUsize::new(consumed).ok_or(…)?`: a comparison such as `if consumed == 0` is itself a mutant, and flipping it spins the loop until the timeout.
- Kill a missed mutant with a test, or exclude it with a reason. Don't leave it.
- Every exclusion (`exclude_re`, `#[mutants::skip]`) carries a comment saying why.
