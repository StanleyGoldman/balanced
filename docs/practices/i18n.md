# Internationalisation

Every user-visible string is a Fluent message, and every number and date is formatted by ICU4X. `balanced_i18n` owns both, behind `Localizer`. The decisions behind this are in issue #13, "Choose the internationalisation approach".

## Looking text up

- In `balanced_ui`, write `fl!(i18n, "message-id", arg = value)`, where `i18n` is the `&Localizer`. Add an attribute after the id: `fl!(i18n, "account-bar-total", "tooltip")`. The macro is `crate::i18n::fl`, which wraps `i18n_embed_fl::fl!` and adds the pseudo-locale's brackets. Call `i18n_embed_fl::fl!` or the loader directly only from that wrapper.
- Ids and attributes are string literals. `fl!` checks them, and each argument name, against `en-US` at compile time.
- For enum-driven text, `match` each variant to its own literal id. Building an id with `format!` defeats the check.
- Store message ids in state, not translated `String`s. Text is looked up every frame, so a language switch shows on the next frame (call `ctx.request_repaint()` after switching).
- Review flags a raw string literal shown in a widget, and an `en-US` id that no code uses. Neither is a CI check.
- Build one sentence per message. Pass the parts that change as arguments rather than concatenating translated fragments, because word order differs between languages.

## Writing messages

All messages live in `crates/balanced_i18n/locales/<language>/balanced.ftl`, grouped under Fluent section comments (`## Menu bar`, `## Register`).

- **Ids** are kebab-case and start with their area: `menu-file-open`, `account-bar-total`, `register-column-payee`, `dialog-new-account-title`.
- **Attributes** hold other text for the same widget: `.tooltip`, `.a11y`.
- **Terms** hold the app name and the `CONTEXT.md` glossary words: `-brand-name`, `-account-bar`. Refer to them with `{ -account-bar }` so that a translator changes each glossary word in one place. A translation that uses a term defines that term in its own file.
- **Arguments** are snake_case, because `fl!` arguments are Rust identifiers.
- **Plurals** use a selector on a number argument: `{ $count -> [one] … *[other] … }`.
- **Money and dates** reach a message as strings already formatted by `Localizer`. Plain counts are passed as numbers, so plural selection works and the formatter hook formats them in the formatting locale.
- Add every new message to `en-US` first. It is the only complete locale.

## Translations

- Agents write `en-US` messages only. When asked to add a translation, an agent takes each string from a published translation of comparable software (GnuCash, KMyMoney, KDE, LibreOffice) and cites the source in the PR. It flags any wording it had to assemble or coin for a native speaker to check.
  - Where the German files are: GnuCash's `po/de.po` on the `stable` branch of github.com/Gnucash/gnucash; KMyMoney's `po/de/kmymoney.po` inside the release tarball at download.kde.org/stable/kmymoney/<version>/ (KDE's websvn l10n paths return 404); Qt's `translations/qtbase_de.ts` in github.com/qt/qttranslations, which holds the key and modifier names (Strg, Umschalt); LibreOffice's `source/de/<module>/messages.po` in github.com/LibreOffice/translations. Other languages sit beside `de` at the same paths.
  - Match each `en-US` string against the files' `msgid`s with mnemonics (`_`, `&`) stripped and fuzzy entries skipped.
- A message or attribute a translation lacks falls back to `en-US`. Debug builds log each one with `warn` when the language loads.
- When you rename or delete an `en-US` id, attribute or argument, change every translation that has it in the same PR. The `locales` test in `balanced_i18n` fails on a translation with an id or attribute `en-US` lacks, on a translated message whose `$variables` differ from `en-US`, and on a term used but not defined. It only reports untranslated messages, as a count per locale.
- A new locale is a new folder under `locales/` named by its language tag. Name it by the base language (`de`, not `de-DE`) unless the text really differs by region.

## Locales

- **Two locales, kept apart.** The text language picks the messages. The formatting locale picks number and date formatting. Both default to the OS locale.
- **Fallback chain:** the text language, then its base language, then `en-US`, keeping only shipped locales. A sibling region never matches: `de-AT` reaches `de` but not `de-DE`.
- **Pseudo-locale `en-XA`:** the `en-US` text with accented letters, doubled vowels and `[…]` around each message, formatting in `de-DE` by default (`Localizer::pseudo()`). Use it to find hard-coded strings, truncation and fixed widths. A string that shows up unaccented on screen did not come through `fl!`.
- The formatter hook formats numbers inside messages with thread-local state. Build the `Localizer`, and look text up, on the UI thread.
- Right-to-left scripts are out of scope until egui supports bidi. Fonts beyond egui's default font cover only Latin, Greek and Cyrillic, so CJK needs a bundled font first.

## Tests

- UI tests use `Localizer::for_tests()` (feature `test-support`, a dev-dependency feature): `en-US` text and formatting, with Fluent's bidi isolation marks off so that strings compare equal to literals.
- Unit-test formatting in `balanced_i18n` with explicit locales, never the OS locale.
